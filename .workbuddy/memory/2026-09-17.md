## frida `import` 语法错误修复（SyntaxError: expecting '('）
- 根因：Python 版 `session.create_script(js)` 默认用 **Duktape 运行时**，不认 ES module 的 `import "frida-il2cpp-bridge";`，第一句就解析失败；光加 `runtime="v8"` 不够，因为 `import` 仍需模块解析。
- 修法：`frida-il2cpp-bridge` 必须**打包成自包含 IIFE**，用 V8 运行时加载。
  - 沙箱 npm 极慢（默认源卡死），换国内镜像 `--registry=https://registry.npmmirror.com` 后秒装。
  - 用 `esbuild` 打包（比 `frida-compile` 可靠，后者在沙箱卡死）：`esbuild frida_dump.js --bundle --format=iife --platform=neutral --outfile=frida_dump.bundle.js`。
  - 注意：node_modules 里只装一个包时，`npm install <另一个包>` 会 prune 掉之前的包；必须先把所有依赖写进 `package.json` 的 `dependencies` 再一次性 `npm install`，否则被清掉。
- 产物：`tools/frida_dump.bundle.js`（~140KB，IIFE、0 个顶层 import、内联 bridge，`Il2Cpp` 全局可用）。`frida_host.py` 已改为优先加载该 bundle 并 `create_script(js, runtime="v8")`。
- 临时目录/文件：打包在 `C:\aB\ucf_bundle_tmp`；临时日志曾落在 `tools/_*.txt`/`_*.log`，已移出项目到 `C:\aB\ucf_tmp_cleanup`（沙箱 safe-delete 拦截 Remove-Item，无法删除，故用 Move-Item 移出）。

## `GameManager` 实例 null → access violation 崩溃修复
- 现象：IL2CPP ready 后 `myPlayer = null` / `GameManager instance = null`，随后 `access violation accessing 0x0`（栈在 `field` 访问）。
- 根因（已排除类名/命名空间问题）：`dump.cs:230773` 确认 `GameManager` 命名空间为空、`get_instance()` 继承自 `Singleton<GameManager>`、`myPlayer` 是静态字段(0x0)、`allPlayers` 是实例字段(0x14)。旧脚本在 `Il2Cpp.perform` **初始化阶段**就一次性读 `myPlayer`/`get_instance()` 并缓存——此时游戏场景未加载、单例尚未创建，拿到 null 后对其调 `.field()` 即崩。**纯时序问题，非静态定位错误。**
- 修法（改 `frida_dump.js` 并重打包）：
  - 把 `GameManager` 实例、`myPlayer`、`allPlayers` 改为**每帧 setInterval 内重新读取**，绝不在 init 阶段读取后缓存。
  - 全程 null 安全：任何为 null 的分支只 `return`/跳过本次 tick，不再对 null 调 `.field()`。
  - 加**启动探针**：init 时各打印一次 `get_instance`/`myPlayer` 方法字段是否找到，避免静默死等。
  - GameManager 就绪前每 3 tick 打印 `等待 GameManager 实例（尚未创建）...`，就绪后自动开始出帧。
- 重打包：复制源到 `C:\aB\ucf_bundle_tmp` 再 `esbuild --bundle --format=iife --platform=neutral`，拷回 `tools/frida_dump.bundle.js`（仍 ~141KB，IIFE、0 import）。
- 验证：待用户本机重跑确认从 `等待 GameManager...` 过渡到正常出帧、矩阵/坐标随视角移动变化。若仍一直 `等待`，则需考虑 `get_instance` 名字随 bridge 版本变化（开 `DISCOVER=true` 重打包看真实导出名）。

## 按需清理残留进程（用户要求）+ 热键重写
- 需求：跑之前先把残留同名进程杀干净。实现 `cleanup_before_launch()`：默认启动路径先 `taskkill /F /T /IM UnityCrossFire.exe` 清干净，再 `Popen` 唯一实例；`--no-cleanup` 关闭；`--no-launch --kill-stale` 只杀“没加载 GameAssembly.dll”的空壳、保留真游戏。
- **坑**：`taskkill` 的输出是 **GBK**，`subprocess.run(..., text=True)` 会在 reader 线程抛 `UnicodeDecodeError`（stdout/stderr 都读不出来）。改为按字节捕获再 `decode("gbk", errors="replace")`，并把 `rc==128`（没有找到进程）当正常情况。
- **热键重写**：`SetWindowsHookEx` 低级键盘钩子的 ctypes 回调在 64 位下必崩 `OverflowError: int too long to convert`（`lParam` 是 64 位指针，`CallNextHookEx` 的 argtypes 未声明）。**弃用钩子**，改 `GetAsyncKeyState(VK_INSERT) & 0x8001` 轮询（`0x8000` 当前按下 + `0x0001` 自上次调用以来按过，防快速点按漏检），无回调、无溢出；`ENTER` 也可触发。
- 数据源优化并重打包：`INTERVAL_MS=50`（原 1000ms 太慢，叠加层没法看）、`WARN_MS/REPORT_MS` 改为时间戳节流（原来按 tick 计数在 50ms 下会刷屏）、每 5s 打 `已发送 N 帧` 心跳、脚本 load 瞬间先打 `frida agent loaded...`（区分“没注进去”与“注进去了在等模块”）。
- **esbuild 路径坑（重要）**：Git Bash 里 `--outfile=/c/aB/...` 会被 esbuild 当成 `C:\c\aB\...`（本次还遇到"Done"但文件没更新）。**必须输出到本地文件名再 `cp` 回工程**。
- 顺带修 `tools/replay.py`：`sample_session.json` 默认路径不解析脚本目录，从工程根跑会 FileNotFoundError；加 `_resolve()` 兜底。

## 打通到"调用矩阵方法"这一步：实例方法多传 this + 32 位结构体按值返回
用户贴回的运行日志：进程选择正确（pid=7544，GameAssembly.dll=YES）、`IL2CPP ready`、
`找到 Singleton.get_instance: true`、`找到静态字段 myPlayer: true`，但每帧刷
`couldn't invoke method get_worldToCameraMatrix as it needs 0 parameter(s), not 1`。

- **根因**：`frida-il2cpp-bridge` 里 `obj.method(名, 参数个数)` 返回的是**已绑定实例**的方法，
  `.invoke(...)` 只接方法自己声明的参数，**不能把 this 当参数传**。旧代码 `invoke(cam)` 多传一个 → 报错。
  已全面修正（`readVec3(t.method("get_position").invoke(t))` 等同类型错误一并修掉）。
- 顺带核实 bridge 实现（读 bundle 源码确认，不是猜）：
  - `Method.invoke` 对非静态方法直接 raise；`bind()` 返回 Proxy，`invoke` 被替换为 `invokeRaw.bind(target, handle)`。
  - `Class.tryMethod` 走 `classGetMethodFromName`（能搜到 private，如 `_Injected`；也沿父类链，
    所以 `GameManager.method("get_instance")` 能拿到声明在 `Singleton<T>` 上的方法）。
  - 原始类型返回：数字原样返回、bool 走 `!!value`、enum 返回 number。
- **新增第二个决策：32 位下不走"结构体按值返回"**。`Matrix4x4`(64B)/`Vector3`(12B) 按值返回依赖
  frida 的结构体返回 ABI（i386 上易翻车）。dump.cs 里有同名的 `*_Injected(out T)`（void + out 指针），
  改用 `Memory.alloc(64/12)` 当 out 缓冲 + 裸内存读 float。`frida_dump.js` 先探测 `_Injected`，
  缺失才回退公开 getter 并打印模式（`矩阵读取模式: injected|getter`）。
- **血量改裸内存读**：`HealthData.currentHealth@0x8`（maxHealth@0x1C）；`ObscuredInt`
  `currentCryptoKey@0x0 / hiddenValue@0x4 / inited@0x8 / fakeValue@0xC / fakeValueActive@0x10`（大小 0x14，
  与 0x1C-0x8 吻合）。明文 = `hiddenValue ^ currentCryptoKey`。**不调 `InternalDecrypt()`/`GetDecrypted()`**：
  它们是值类型方法，而 bridge 的 `ValueType` 字段访问/方法绑定带 `−headerSize` 补偿，
  从"字段读出的 ValueType"再取字段/调方法会差一个 header。启动时打印 `ObscuredInt 自检` 并用
  `fakeValue` 交叉验证（`✓一致` = 算法与偏移都对）。
- 屏幕尺寸改用 `Screen.get_width/get_height()`（原来硬编码 1280x720），帧里 width/height 现在是真值。
- **新增 `callMethod()`**：统一实例调用入口，`obj.tryMethod` 找不到时沿 `obj.class.hierarchy()`
  找声明类再 `bind(obj)`（`Component.get_transform` 这类继承成员也能拿到），避免静默 null。
- **修复 `--game` 裸文件名 `[WinError 2]`**：新增 `resolve_game_path()`，按
  环境变量 `UCF_GAME` → 已知安装目录 → 当前目录 → 工程父目录 顺序解析；找不到就打印三种正确写法。
  `inject()` 改成接收 js 路径（日志顺序按真实执行顺序：候选进程 → 选定 → 加载脚本 → attach → 注入完成）。
- **新增 `tests/test_dump_contract.py`**（离线契约测试，8 项）：解析 `il2cpp_dump/dump.cs` 校验
  Matrix4x4 列主序布局（前 4 字段必须是 m00,m10,m20,m30）、`*_Injected` 签名、
  `Screen.get_width`、`GameManager:Singleton<GameManager>` + 静态 myPlayer / 实例 allPlayers、
  ObscuredInt 五个偏移 + 0x14 间距、Entity/Player 方法名，以及"frida_dump.js 引用的 12 个方法名与 dump 一致"。
- 回归全绿：`tests/test_process_selection.py` 8/8、`test_dump_contract.py` 8/8、黄金样本 3/3、
  bundle 与源码重打包哈希一致（b455c6538798bf865ec1690067aeb2ac，145808 字节，0 顶层 import，node --check 通过）。

## level3/4 硬崩溃定位：泛型基类上的 get_instance() + 数组下标坑（并新增 --probe 单步探测）
- 二分结果：`--level 3` 与 `--level 4` 都在打印完 `矩阵读取模式: injected` 后
  `process-terminated`（不是 Ctrl+C 的 application-requested）→ 崩在“取单例 / 遍历玩家 / 读坐标”。
- **头号嫌疑（有 dump 实证）**：`Singleton<T>.get_instance()` 在 dump.cs 231205 标着
  `RVA: -1 Offset: -1`（开放泛型定义无本地代码），只有 `Singleton<GameManager>` 的实例化版本
  才有 RVA 0x4953F0；且 IL2CPP 共享泛型方法带**隐藏 MethodInfo\* 参数**，按普通签名调用
  → 被调方解引用垃圾 MethodInfo\* → **AV，进程瞬间消失、Player.log 无异常栈**，与现象完全吻合。
  改为两条**零 invoke** 的取单例路径：① 静态 backing field `Singleton<T>.<instance>k__BackingField`
  （dump 231189，`public static T instance{get;set;}` 自动生成）；② `Il2Cpp.gc.choose(GameManager)`
  堆扫描（5s 缓存）。`get_instance()` 降级为兜底，**默认关闭**，需 `--allow-get-instance`。
- **第二个静默 bug**：bridge 的 `Il2Cpp.Array` 只有 `.length` / `.get(i)` / 迭代器，
  **没有 `arr[i]` 下标 Proxy**。旧代码 `allPlayers[i]` 恒为 `undefined` → `if (p)` 跳过 →
  `players` 永远是空数组且不报错。改用 `.get(i)`，并对 length 加 `MAX_PLAYERS=128` 上限兜底。
- **新增 `--probe` 单步探测**：注入后按固定顺序把 16 个关键调用各做一遍，每步前后各打一行日志
  （setInterval 状态机，步间 250ms，让日志来得及送出），**进程崩掉时最后那行 `▶ [n/16]` 即崩点**。
  顺序刻意把高危的 `get_instance()` 放最后。探测跑完才 `startFrameLoop()`。
  → 把“临时改脚本做实验”固化成工具能力。
- `frida_host.py`：`build_script_source()` 与 `inject()`/`run_live()` 增加
  `probe` / `allow_get_instance` 透传（UCFG 键 `probe` / `allowGetInstance`）；`--help` 同步。
- `tests/test_script_config.py` 扩到 8 项：新增 UCFG 新开关默认关闭、--probe/--allow-get-instance
  透传且键名一致、16 步探测锚点在**源码与 bundle 中同步且 get_instance 排最后**、
  取单例不默认调 get_instance + 数组走 `.get(i)` + 有长度上限。
- 回归：8/8 + 8/8 + 8/8 + 黄金样本 3/3 + bundle 154092 字节 / 0 顶层 import / node --check 通过 /

## --probe 定位成功：崩在 get_isDead()，真因是「frida 线程 ≠ Unity 主线程」
单步探测输出（16 步，崩在第 13 步，前 12 步全过）：
  4 静态 myPlayer→0x30736720   5 <instance>k__BackingField→0x8c2c828
  6 堆扫描找到 1 个 GameManager（与 5 同一 handle，互相印证）
  7 gm.allPlayers @0x2e609ea0   8 length=30   9 get(0)→0x30736720
  10 get_transform→0x371412f0   11 get_position_Injected→(7.53,11.97,25.24)
  12 get_team→GlobalRisk        13 **get_isDead() → process-terminated**
→ 取单例两条新路（静态 backing field / 堆扫描）都验证成功；坐标、队伍、数组遍历全通。

- **真因（有 dump 实证，非猜测）**：frida 的 `setInterval` 跑在 **frida 自己的线程**，
  不在 Unity 主线程。判读口诀 —— **看 dump 里有没有 `[CompilerGeneratedAttribute]`**：
  | 方法 | 标记 | 结果 |
  |---|---|---|
  | `Entity.get_team()` @0x1D80E0 | 有（字段直读） | 通过 |
  | `Entity.get_isDead()` @0x1D80B0 | **无**（真实方法体） | **AV** |
  | `Player.get_isMyPlayer()` @0x2C3C80 | **无** | 同类隐患 |
  另：`HealthData.isDead` 也是真实方法体 → 死亡状态根本不该靠调方法。
- **两条对策（已落地）**：
  1. **取帧调度到 Unity 主线程**：bridge 有 `Il2Cpp.mainThread`（= attachedThreads[0]）
     与 `Thread.schedule(block)`（有 SynchronizationContext 时走 SendOrPostCallback+Post
     返回 Promise，否则回退 `Process.runOnThread`）。新增 `callOnMainThread()`，
     调度失败只报一次并永久回退 frida 线程；`MT.busy` 防异步重入堆积（Post 是异步的）。
     默认开，日志打 `[*] 取帧调度：Unity 主线程`；`--no-main-thread` 可关。
  2. **isDead 改由血量推导** `hp<=0`（血量本来就是裸内存明文，零 invoke）。
     `get_isDead()` 降级为 `--allow-is-dead`，探测里排在**倒数第二**（get_instance 仍最后）。
- 探测改为 Promise 链 + 每步 3s 超时看门狗（主线程 Post 不回时不会把探测卡死）。
- 顺手修：`out.isLocal` 之前恒为 `false`，改为由 `isMyPlayer` 推导。
- `frida_host.py`：`build_script_source()`/`inject()`/`run_live()` 增加
  `allow_is_dead` / `main_thread`（UCFG 键 `allowIsDead` / `mainThread`，后者默认 true）。
- `tests/test_script_config.py` 扩到 10 项：新增「isDead 默认由 hp<=0 推导」
  与「取帧走主线程调度 + busy 防重入」；探测顺序断言加“get_isDead 倒数第二”。

## 误判"投影公式错了"：实算是第三人称相机贴脸，NDC 才是对的裁剪判据
用户看到 `[local] screen=(-153,4121)`（屏幕 800x600）判定投影公式错（怀疑 VP 顺序/Y 翻转）。
**用纯手算行主序 P·V 独立复算 = (-152.6, 4121.1)，逐位吻合 → 公式没错。** 且 tick=3 帧的
敌方 (797,215) 复现了实测日志值（实算 797.4, 215.3），敌方 (200,443)/(166,420) 也全在屏幕内。

- **真因**：从 w2c 反推相机世界位置 cam = -Rᵀ·t ≈ (10.688, 14.170, -2.066)，
  与本地玩家 (10.57, 13.23, -2.00) 只差 (0.12, -0.94, 0.07) —— **相机挂在玩家头顶 0.95m**。
  透视除法 w=0.1096 → ndc_y=-12.73 → 屏幕坐标放大几十倍。数学正确但不可画。
- **新增 `esp_core.camera_position(V)`**（cam = -Rᵀ·t，列主序取 R[row][col]=V[c*4+r]、t=V[3*4+r]），
  并给 Mark 加 `dist` / `clipped` 字段；`project_frame(..., ndc_clip=NDC_CLIP)`。
- **关键教训：裁剪判据必须用 NDC 幅度，不能用距离。** 先写了 `dist < 1.5m` 的距离阈值，
  结果合成样本（世界尺度是"1 单位"不是米，玩家离相机 0.65）被误裁成全部不可见。
  改成 `|ndc| > 3.0`（NDC_CLIP）—— 与世界尺度无关。
- **`world_to_screen` 不做裁剪**，仍返回原始数学值（测试里专门断言 screen 仍是 -152.6/4121.1），
  裁剪只在 `_make` 里标记 `clipped`，叠加层跳过。控制台打印成 `[不可画: ndc 超界, 0.95m]`。
- **另一个真 bug：team 是 boxed 对象，队友识别整个失效。**
  `Team` 是 `enum : int`（dump 231002，value__，0=BlackList 1=GlobalRisk 2=Neutral），
  但 bridge 把 `get_team()` 返回值按 OBJECT 处理、**不解包 value__**（`fromFridaValue` 的
  enum 分支只在 type 是 VALUE_TYPE+isEnum 时才走，这里走的是 OBJECT 分支），
  传到宿主是 `{handle,type}` → 两个对象永不相等 → 全员被判 enemy。
  改为 `readTeamOf()`：裸读 `Entity.<team>k__BackingField`（0x1C）的 4 字节 int，零 invoke。
  探测第 12 步改成同时打印"裸读 int vs get_team() 对象"做交叉验证。
- **叠加层尺寸硬编码 1280x720 而游戏是 800x600 → 会整体放大 1.6 倍错位**（上 overlay 必踩）。
  `overlay_tk` 新增 `game_client_rect()`：用 `FindWindowW("UnityWndClass")` +
  `GetClientRect` + `ClientToScreen` 对齐客户区（**刻意不用 EnumWindows 回调**，
  64 位 ctypes 回调会 OverflowError，本项目已栽过一次）；拿不到窗口就 `fit()` 跟随帧分辨率；
  对齐成功后 `aligned=True` 不再改。`frida_host.on_message` 每帧调 `OVERLAY.fit(w,h)`。
- 小改进：`everHadGm` 区分"尚未创建"与"退出对局已销毁"（回菜单时别再干等）；
  allPlayers 日志改为显示有效数与 null 槽位数（30 个槽位只有 10 个有效）。
- **新增 `tests/test_projection_calibration.py`**（8 组/24 项）：
  fixture 用真实帧 `tests/fixtures/real_frame_level3.json` 与 `..._tick3.json`。
